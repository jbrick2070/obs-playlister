Status: 2026-10-24. Approved by the operator; decisions are recorded in section 14.

This file is the source of truth for what obs-playlister must do. It has two
halves: what the upstream plugin does today (so nothing is lost by accident),
and what obs-playlister adds. Rule from the project brief: before any upstream
behavior is removed or replaced, the requirement it served is recorded here
first.

Requirement IDs are stable. PLAN.md and commit messages refer to them.
"src N" means src/media-playlist-source.c line N at commit f8d90bd.

## 3. Upstream behavior inventory (what Media Playlist Source 0.1.3 does today)

Everything here is read from the source at commit f8d90bd. Each item is a
requirement to keep unless a later section says otherwise. "MPS" means the
upstream plugin.

### 3.1 Module and source registration

| ID | Behavior |
|----|----------|
| R-UP-1 | One module. `plugin-main.c` registers one source and logs load/unload with the plugin name and version via `obs_log()` from `plugin-support.c`. It exports no `obs_module_name`/`obs_module_description` (see R-PLAT-9). |
| R-UP-2 | Source id `media_playlist_source_codeyan` (media-playlist-source.h:158), type INPUT, flags VIDEO, CUSTOM_DRAW, AUDIO and CONTROLLABLE_MEDIA, icon MEDIA. Display name from locale key `MediaPlaylistSource` (src 446-450). |
| R-UP-3 | The source owns one private child `ffmpeg_source` named `current_media_source` created with `log_changes=false`, added as an active child, enumerated via `enum_active_sources`. Video renders by drawing the child; width/height come from the child. |
| R-UP-4 | Audio: an audio capture callback on the child pushes frames into per-channel deques; `video_tick` drains them into `obs_source_output_audio` on the playlist source. (`audio_render` exists but is commented out and unused.) |
| R-UP-5 | A `select_index(int media_index, int folder_item_index)` proc handler exists for scripts. Actual behavior (src 249-263): an out-of-range `media_index` does nothing; an out-of-range `folder_item_index` falls back to 0. The README claims `media_index` clamps to 0; the README is wrong. obs-playlister keeps the actual behavior and adds a log line for the ignored call (R-BEH-2). |

### 3.2 Settings (persisted keys)

| ID | Key | Behavior |
|----|-----|----------|
| R-UP-10 | `playlist` | Editable list of files and URLs (`OBS_EDITABLE_LIST_TYPE_FILES_AND_URLS`), each item has `value` and a `uuid` id. File dialog filter lists video and audio extensions; Phase 2 adds a still-image group and Phase 3a a playlist-file group (`.m3u`, `.m3u8`, `.pls`). |
| R-UP-11 | `loop` (default true) | Wrap from last to first on next, first to last on previous, and auto-continue at end. |
| R-UP-12 | `shuffle` (default false) | VLC-4-derived Fisher-Yates shuffler with history: adding/removing items does not reshuffle; previous still works across manual selection; reshuffles when the cycle ends without repeating the last item first (`NOT_SAME_BEFORE = 1`). It uses `rand()` and nothing in the repo seeds it, so the order may repeat across OBS restarts (verified at build, PLAN section 8). |
| R-UP-13 | `visibility_behavior` (int, default stop/restart) | Four modes: Stop when hidden / restart when shown; Pause / unpause; Always play; Stop when hidden / play next when shown (deactivate stops and loads the next item; the child's `restart_on_activate` starts it when shown, src 728-732, 1205-1210). Kept as is. |
| R-UP-14 | `restart_behavior` (int, default current file) | On media restart: restart the current file, or play the first file. |
| R-UP-15 | `hw_decode` | Passed to the child ffmpeg_source ("Use hardware decoding when available"), which then decodes on the GPU (NVDEC on the RTX 5080). The plugin has no decode path of its own; all playback goes through OBS's media source. NVENC is OBS's encoder for streaming and recording and is not affected by the plugin. Upstream registers no default, so it is off for new sources (src 955-963); obs-playlister defaults it to on (D-11), and a source's saved value still wins. |
| R-UP-16 | `close_when_inactive` | Passed to the child ffmpeg_source, with tooltip. |
| R-UP-17 | `speed_percent` (1..200, default 100) | Passed to the child; changing it restarts the video (warning text shown). |
| R-UP-18 | `current_media_index`, `current_folder_item_filename` | Saved in `save()` so the same item resumes after OBS restart. Folder items are matched by filename after a rescan, because indexes shift. Generalized by R-KEY-2. |
| R-UP-19 | `current_file_name` (info text) | Shows `N: path` or `N-M: path` of the playing item. Only refreshes on settings change, Play Selected, or the Refresh Filename button; never on media end (documented OBS limitation, crash risk). |
| R-UP-20 | `select_file` + "Play Selected File" button | Dropdown of every item (`N` or `N-M` keys) and a button that jumps to it and signals `media_next`. The `N-M` values are positions, so a list that changes while Properties is open could jump to the wrong item. From Phase 2 the stored value is an identity `<row_uuid>:<occurrence>:<item_key>` (split at the first two colons; the key is the rest, verbatim), and a stale identity gives a "list changed, press Refresh" status instead of a jump. Display text everywhere (Current File and Select File) is `N-M: title (location)` when the entry has a title (`#EXTINF`, feed item title), else `N-M: location`. As built (Phase 2 step 4): `core/keys.c` writes and reads the identity (`pl_selection_format`, `pl_selection_parse`); a file row is `<row_uuid>:0:`. The button looks the identity up and plays it under one hold of the list lock. An item whose occurrence is gone is stale (no other item of its key stands in, unlike resume), and so is a value that is no identity, such as upstream's `N` or `N-M` saved before Phase 2. The stale message goes to the Current File text until the row status block (R-LIST-5, step 7) takes it, and is logged; Select File goes back to No File Selected, as the dropdown has no entry for the stale value. The `select_index` proc for scripts keeps its positions, as upstream's API. |
| R-UP-21 | child settings | `restart_on_activate` on the child is false for Always play and Pause/unpause, true otherwise. Upstream never sets `clear_on_media_end`, so the ffmpeg_source default `true` applies (obs-ffmpeg-source.c:121 at 33.0.0): the frame clears at each item end. |

### 3.3 Playlist model and folder items

| ID | Behavior |
|----|----------|
| R-UP-30 | A playlist item is a file, a URL (contains `://`), or a folder. A folder item is expanded at update time into `folder_items` (non-recursive, directory entries skipped), filtered by extension against the media/video/audio lists in `media-playlist-source.h`, in the order `os_readdir` returns them (no sort). The extension check (src 140-161) is a case-insensitive substring search for `*<ext>` in the joined filter strings, so partial extensions such as `.mp` also pass; `core/filter.c` replaces it with whole-extension matching (R-DIR-5). Folder items are matched by bare filename (src 320-332, shuffler.c 308-312), which collides once subfolders exist; replaced by R-KEY-1. Folder items carry no `id` (src 1145-1153). This two-level model (row, sub-item) is kept and generalized by R-LIST-1. As built (Phase 2 step 5, part 2): a folder row is no longer listed in `update`: its provider lists it on a worker (PLAN section 3.3) with the extension filter (R-DIR-5), the subfolder option (R-DIR-1) and the sort (R-DIR-6, default date); the requirement it served, a folder row playing its media files, stands. |
| R-UP-31 | Folder contents are NOT refreshed automatically; re-saving settings rescans. (README "Limitations".) This is the gap the Directory Sorter script filled; replaced by R-DIR-2. As built (Phase 2 step 5, part 2): folder rows follow their folders live (R-DIR-2, R-DIR-3); a settings change no longer rescans, and a running provider takes the new options without a new listing. |
| R-UP-32 | Editing the playlist does not restart the current video, even if items are reordered: the current item is found again by its `uuid`; if its path changed (`item_edited`) playback moves to folder item 0 / restarts the item. |
| R-UP-33 | An empty playlist or an empty folder clears the child source (empty path, stop) so no stale last frame remains. An empty folder encountered during next/previous is skipped. Upstream's `play_media_at_index` also tested `actual_media` right after `set_current_media_index`, which never sets it while the list has files, so a stale or NULL pointer chose between loading and clearing. From Phase 2 step 1.3 that function clears only when it finds no playable row, and the test is removed. |
| R-UP-34 | Missing-files integration: non-URL items that do not exist are reported through `obs_missing_files`, and the callback can relocate or remove them. From Phase 2 this applies to file rows (and Phase 3a playlist-file rows) only: folder rows and UNC rows are handled by the folder provider's `missing` state instead, because the relocation dialog accepts files only and an existence check on an offline share blocks the UI thread. As built (Phase 2 step 4): a row whose folder kind is saved (R-LIST-1) is not reported, so an absent watched folder does not reach the relocation dialog; UNC rows are left out too (step 5 part 3), file rows included, as the requirement says: asking about an offline share would hold up the UI, so a file moved on a share is not offered for relocation and fails as an unplayable entry instead (R-BEH-5). |

### 3.4 Transport and signals

| ID | Behavior |
|----|----------|
| R-UP-40 | Media controls: play/pause, restart, stop, next, previous, get/set time, get duration, get state; all delegate to the child. State is tracked locally too (`mps->state`). |
| R-UP-41 | On the child's `media_ended` signal: advance to next, or if last and not looping, mark ENDED, emit `media_ended`, and reset to index 0. A `user_stopped` flag suppresses the spurious ENDED that follows a deliberate stop/deactivate (OBS 29-31 quirk; still relevant at 33: `media_stopped` emits ENDED unless the state is STOPPED, obs-ffmpeg-source.c 274-286). The flag is sticky: it is set on speed changes and deactivate even when no ENDED follows (src 1197-1199, 724), so it can swallow the next real end. It stays through Phase 1; from Phase 2 step 1.2 the requirement it served (ignore ends caused by our own stop or reload) is met by the player's end attribution (R-THR-1, R-BEH-6) and the flag is removed. The child's `media_ended` is the only child signal connected (src 772-773); there is no failure signal. |
| R-UP-42 | Five source hotkeys: PlayPause, Restart, Stop, PlaylistNext, PlaylistPrev, registered as `MediaPlaylistSource.*` (src 777-790); they act only when the source is showing. |
| R-UP-43 | `obs_source_save()` is called after every index change so the resume point is durable. |
| R-UP-44 | A non-recursive mutex (`mps->mutex`, src 796) guards most file-list and index changes; a second mutex guards the audio deques. Known upstream gaps: `mps_properties` reads `mps->files` after unlocking (src 1033 vs 1077-1081); `mps_update` reads `current_media->path` before locking (1226) and changes `current_media`, `actual_media` and the shuffler after unlocking (1271 vs 1275-1323); `get_total_file_count` is called unlocked from next, prev, get_state and activate (598, 654, 346, 706); `mps_restart`, `mps_end_reached`, the two Properties buttons and `video_render` touch list pointers unlocked. R-THR-1 closes these; see also R-UP-62. From Phase 2 step 1.3 every one of them takes the list lock, as do `save`, the Select File list in `get_properties` and the file count in `get_state`; `update` builds the new list, folder listings included, before it takes the lock. |

## 7. New: remote sources (Phase 3)

| ID | Requirement |
|----|-------------|
| R-REM-1 | M3U / M3U8 / PLS from a local file path or an http(s) URL. Relative entries resolve against the playlist's own location: Windows path rules for a local playlist, RFC 3986 against the final URL after redirects (`WINHTTP_OPTION_URL`) for a remote one. `#EXTINF` titles are kept for display. UTF-8 with or without BOM, LF or CRLF. An `.m3u8` carrying HLS tags (`#EXT-X-TARGETDURATION`, `#EXT-X-STREAM-INF`, `#EXT-X-MEDIA-SEQUENCE`) is a stream, not a list: it becomes one entry played directly by the child, and the log says so. |
| R-REM-2 | RSS 2.0 and Atom feeds (podcasts): each item's `<enclosure url>` (RSS) or `<link rel="enclosure">` (Atom) becomes one entry; items without an enclosure are skipped and counted in the log. Dates are parsed from RFC 822/2822 (`pubDate`) and ISO 8601 (`updated`, `published`). Filter rule, the same as for files (R-BEH-4): when the enclosure URL's path (query removed) has an extension, the extension filter decides; only an extensionless URL is accepted on its `type` (`audio/*`, `video/*`, `image/*`). |
| R-REM-3 | Plain HTTP directory index pages (Apache, nginx, IIS, Python `http.server` style): `<a href>` links whose path extension passes the filter become entries; parent-directory, sort-column and query-only links are ignored. |
| R-REM-4 | Remote lists are re-fetched on the refresh interval (default 5 minutes, minimum 30 s). Each provider has at most one fetch in flight; refresh requests that arrive meanwhile collapse into one pending refresh. A fetch that fails (including HTTP 429 and 503) leaves the last good list in place AND sets the row's error state (R-BEH-2/3), and the next attempt comes at the next interval; it never silently keeps playing a stale list without saying so. Changing the interval updates the running provider; it is not re-created. |
| R-REM-5 | Fetching uses WinHTTP only (no libcurl, no new DLLs), in asynchronous mode (`WINHTTP_FLAG_ASYNC`), because Microsoft documents that a synchronous request must not be cancelled by closing its handle. The status callback is registered with the flags `WINHTTP_CALLBACK_FLAG_ALL_COMPLETIONS`, `WINHTTP_CALLBACK_FLAG_REDIRECT` and `WINHTTP_CALLBACK_FLAG_HANDLES` combined. The fetching worker alone owns and closes its WinHTTP handles (on its stop event or deadline), and a fetch does not return to its worker until `WINHTTP_CALLBACK_STATUS_HANDLE_CLOSING` has run, so no WinHTTP callback can run in the plugin after provider destroy or module unload. Redirects are followed (max 5); resolve, connect and send are bounded at 10 s and receive at 30 s (`WinHttpSetTimeouts`; the resolve default is infinite), with a 60 s overall deadline across redirects and body reads. A fetch is two-phase: headers (status, normalized content type, content length, final URL) first, then the caller cancels (direct media), reads a bounded prefix (sniff), or reads the body up to the cap; the final URL is passed on to the parser as its base. HTTPS certificate errors are errors; gzip/deflate responses are decompressed by WinHTTP (`WINHTTP_OPTION_DECOMPRESSION`) and the size cap counts decompressed bytes; "truncated body" is judged from WinHTTP's request error, and a body shorter than `Content-Length` counts as truncated only when there is no `Content-Encoding`. Each fetch ends in exactly one result: ok, cancelled, timeout, TLS error, too many redirects, HTTP status (non-2xx, with the code), truncated body, body too large, or network error; each maps to one row status message. `winhttp` is linked only into the plugin target, in the commit that adds the fetch code. |
| R-REM-6 | Any XML parser is small, GPL-2.0-compatible, and bundled with its license (R-LIC-4). `third_party/` carries a `.clang-format` with `DisableFormat: true` so the repo-wide format check does not reformat or reject vendored code. |
| R-REM-7 | Every source type gets equal terms: the same sort, filter, mode and error-handling code as folder sources (R-LIST-3, R-DIR-10). |

## 9. Behavior rules (hard)

| ID | Requirement |
|----|-------------|
| R-BEH-1 | It either works or it fails. No hidden opt-ins, no feature gates, no silent fallbacks. |
| R-BEH-2 | A missing folder, an unreachable URL, a parse failure or an unplayable file shows a visible error in the source Properties (R-LIST-5) and a clear line in the OBS log prefixed `[obs-playlister]`. A row whose provider has not published yet shows "scanning", "fetching" or "waiting for N files to finish writing", distinct from "empty" and from an error. Properties shows status when it is opened and when the Refresh button is pressed; it is not pushed into an open Properties window from a worker or media thread (upstream crash note, R-UP-19). The log is the live channel. |
| R-BEH-3 | Never quietly keep playing a stale list. If the live list cannot be refreshed, the error state says so and names the last successful refresh time. |
| R-BEH-4 | Every source type (file, folder, playlist, feed, index) shares the same sort, filter, mode and error paths. |
| R-BEH-5 | Unplayable entries. `media_started` proves nothing (the child fires it right after requesting playback, before any decode, and fires nothing at all when the open fails, R-UP-69). Each load therefore opens a startup window (5 s for local files; 15 s for URLs and UNC paths), checked from `video_tick` against the load epoch. The window advances only while the player is playing and either the source is active or the visibility behavior is Always play with `close_when_inactive` off; a hidden or paused source never times out. Evidence must belong to the new load: before updating the child, the player thread blanks the child's video (so a size kept from a previous still cannot count; the exact call is a Phase 2 step 6 spike), clears the queued audio and the pending-event atomics, sets the new load epoch and a "loading" flag, updates the child, and clears the flag. End events raised while "loading" is set belong to the old media and are discarded; an end raised afterwards carries the current epoch and counts. As built in Phase 2 step 1.2 (verified in OBS 33.0.0 with the runtime harness): libobs applies `obs_source_update` to a video source at that source's next tick on the graphics thread and then raises its `update` signal, so the player waits for that signal after every update; each load first unloads the child (an empty path) with ends ignored until that update has applied, because destroying media that is still opening makes its decoder thread report ENDED (media.c, `mp_media_thread_start`), which otherwise chained loads; the new media's ends count from its own update on. Success is observed progress: the child's media time advances past 0, or it reports a non-zero video size, or (audio-only) the audio capture callback delivers frames after the load epoch was set (it records that epoch in an atomic). In `video_tick` startup evidence is evaluated before a pending end is consumed. An entry fails if the child ends before success, or the window expires without success. A failed entry is logged with its path and skipped. Duration is not used, so live streams and stills are not misread as failures. A failed mark is keyed by the entry and its size and date (file rows are stat'ed at load to get them) and clears only when those change. A "full pass" is every entry of the current flattened list visited once since the last successful play or the last change of any row's `content_revision`; if every entry in one full pass fails, auto-advance stops, the child is cleared, and Properties shows the error, instead of cycling through a broken list. Any successful play, list change, manual selection or manual restart resumes auto-advance. The real OBS 33 failure signatures are recorded at build (PLAN section 8). As built (Phase 2 step 6, part 1; `core/startup.c`, `judge_startup` in `video_tick`): evidence is progress only, the media time past 0 or audio delivered after the load (the capture callback stamps the applied load); the video size does not count, as the spike saw an earlier still's size come back at the start of a later load, so no blanking call is needed. The player records the load whose child update applied; its startup is judged only while that load may still auto-advance (a stop, clear, hide or newer load ends the judging). A still is not failed by its end, only by the window, and its end waits until its startup is decided (otherwise a corrupt still would be advanced past at tick rate); an end also waits while the newest load has not been judged yet, as it can arrive before the player records that load. A failure at the end of the list stops the child, as a timed-out URL may still start later (OBS retries it by itself); a user stop lifts the stopped state, so nothing starts by itself afterwards. A failed entry is logged and marked: a folder item by location, size and date (so a replaced file is tried again), a file row or URL by location until the next list change; auto-advance, next, previous and shuffle pass over marked entries. When nothing that may play is left the child is cleared, auto-advance stops and the log says so; a list change, a snapshot that brings something playable, Play or Restart (which first tries the failed entries again) resume it. The Properties status for it comes with step 7. |
| R-BEH-6 | Our own stops never advance. STOP, CLEAR and the hide-stop of a visibility behavior clear the current load's "auto-advance eligible" flag and any pending end before they reach the child; only an end on an eligible load advances. RESTART is a new load with a new epoch and startup window. Same-path reloads (a one-item list looping, newest-only replaying the same file, Play Selected on the current item) restart the child explicitly, as upstream's `should_restart` does (src 218-243), because updating the child with an unchanged path does not restart it. Every executed index change marks the source for a save (R-UP-43). |

## 10. Threading and lifecycle

| ID | Requirement |
|----|-------------|
| R-THR-1 | The list mutex guards every read and write of the entry list, current item pointers and the shuffler, including in `get_properties` and `save`. No libobs call that can call back into the source (`obs_source_update`, `obs_source_media_*`, `obs_source_save`, parent signals) is made while holding it. Each source has one dedicated player thread, the only code that changes the child source. Decisions made under the list lock become owned commands (copied path, key, kind and flags) appended in order to one FIFO while the lock is held, and the player thread is woken; it executes them in order. Nothing is dropped by age: a load followed by a pause performs both. The load epoch (which load is current) is separate from the command sequence. The child's signal handlers take no lock: `media_started`, `media_ended` and the audio capture callback only write atomics (libobs `os_atomic_*`). Automatic advance is decided in `video_tick` from those atomics, in a bounded loop that skips empty containers, and executed as commands on the player thread, so nothing recurses on the media thread and the graphics thread never waits on a load. (libobs itself runs the child's update callback at the child's next video tick on the graphics thread; our code never calls `obs_source_update` from there, and the player thread waits for the child's `update` signal so that commands keep their order.) |
| R-THR-2 | Container rows each have one worker thread (256 KB stack); file rows have none and are built synchronously. Workers build immutable snapshots of plain entries; ownership passes to the source on publish. `pl_provider_create` copies every argument the worker will use (location, row uuid, options, filter string) before returning. The source assigns each provider instance a unique instance id and registers it as the row's expected instance under the list lock before `pl_provider_create` starts the worker (and rolls the registration back if creation fails), so the first snapshot can never be lost. A snapshot is accepted only from the row's registered instance; generation numbers order snapshots only within one instance. As built (Phase 2 step 5, `providers/provider-folder-win.c`): the worker is a `CreateThread` thread with a 256 KB stack reservation; create copies location, options and filter; snapshots are published only when something the receiver sees changed, and `content_revision` bumps only when the membership (entries and versions, in any listing order) changed. Part 2: the source keeps a registry of row providers (row uuid, path, include-subfolders, instance id); a snapshot is applied only for an instance in the registry and only to the folder row with that uuid. |
| R-THR-3 | Provider stop is idempotent: set the provider's stop event; the worker, which alone opens and closes its directory handle, wakes from `WaitForMultipleObjects`, calls `CancelIoEx`, waits for the overlapped call with `GetOverlappedResult(..., TRUE)` before freeing its buffer, and closes the handle; WinHTTP handles are closed by the fetching worker (R-REM-5); blocking calls a stalled share can hang in (enumeration, the probe open) are interrupted with `CancelSynchronousIo` on the worker thread; then join and free any unconsumed snapshot. No worker publishes after join. Recovery from `missing` or `rescan-only` re-opens the directory handle rather than re-arming a dead one. Providers are created and destroyed only in `update` and `destroy`, never while holding the list mutex and never from anything reachable from `publish`: under the list lock the affected providers are detached (their instance ids retired) and replacement ids registered; the lock is released; the old providers are destroyed and joined; the replacements are created. In `destroy`, in order: destroy every provider; stop and join the player thread; disconnect the child's signals and remove its audio capture callback (R-UP-70); release the child; free state. As built (Phase 2 step 5, `providers/provider-folder-win.c`): stop sets the stop event; the worker cancels its armed call with `CancelIoEx` and waits for it with `GetOverlappedResult(..., TRUE)` before closing the handle; destroy calls `CancelSynchronousIo` on the worker every 100 ms until it exits, as the worker may not have entered a stuck call when the first one comes. Part 2: under the list lock `update` keeps a row's provider and moves its items to the replacement row while uuid and path are unchanged, registers new instance ids for new or moved rows, and takes the providers of rows that are gone out of the registry; after unlocking it destroys those, creates the new ones and hands changed options to the running ones. `destroy` destroys every provider before anything else. |
| R-THR-4 | Snapshot applies run on the publishing worker, not on the video thread, under the list lock. Every change of the list, from `update` or from `publish`, calls `shuffler_update_files()` while the old storage is still alive, whether shuffle is on or off (upstream skips it when shuffle is off, src 1257-1273, which would leave the shuffler pointing into freed storage once applies happen on workers). A row's location change clears its entries and makes it awaiting (R-KEY-2, R-UP-32); a provider re-created on the same location (include-subfolders change) keeps the row's last entries until the new instance settles, so playback keeps its place and the shuffler keeps that row's history. View-option changes (filter, sort, direction, mode, N, refresh interval) are applied to the running provider, which re-publishes from its cached raw list without rescanning. `publish` only sets a save-dirty flag; `video_tick`, which holds no plugin lock, calls `obs_source_save` when the flag is set and at least one second has passed. As built (Phase 2 step 5, part 2): the snapshot apply runs on the provider's worker under the list lock: renames re-key the old items (`pl_merge_rekey`) and carry the remembered and resume keys, the visible entries become the row's items, `shuffler_update_files` runs while the old items are alive, and the playing item is found again by exact key and occurrence. An include-subfolders change re-creates the providers and the rows keep their items until the new instances publish. |
| R-THR-5 | Paths are UTF-8 inside the plugin and converted to UTF-16 only at Win32 calls. OBS stores paths with forward slashes, and `\\?\` turns off Win32 path normalization, so the boundary helper first canonicalizes with `GetFullPathNameW` (backslashes, `.`/`..` resolved, no trailing separator except at a root, any existing prefix removed) and only then adds `\\?\` or `\\?\UNC\`. `pl_entry.location` stays an ordinary path, so the child receives what upstream gives it (whether the child opens paths longer than 260 characters is verified at build). As built (Phase 2 step 5, `providers/provider-folder-win.c`): `GetFullPathNameW`, trailing separators removed except at a root, then `\\?\` or `\\?\UNC\`; a path that already has a prefix keeps it, with '/' turned into '\' as the prefix turns normalization off; entry locations are the row path, "/", and the relative path, as upstream built them. |
